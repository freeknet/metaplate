# Framework and runtime support

Which frameworks and runtimes each entry point supports, and the release evidence behind each claim.
## Runtime and dynamic-route safety

The upstream links below define each framework's routing and deployment
contract; this guide documents the Metaplate-specific mapping and the narrower
set actually exercised by the release gate.

| Integration | Official framework reference | Supported runtime | Release evidence |

| Edge isolates that forbid run-time Wasm compilation (Cloudflare Workers, Vercel Edge) | [Workers WebAssembly](https://developers.cloudflare.com/workers/runtime-apis/webassembly/) and [Vercel Edge runtime](https://vercel.com/docs/functions/runtimes/edge) | **Not supported**, by `metaplate/edge` or `metaplate/node`; use the provider's Node runtime or build-time images | Cloudflare Workers: a Worker built from the packed 0.8.0 tarball returned 500 for every render under `wrangler dev --local` (workerd) on 2026-11-01, because Satori's bundled HarfBuzz reads `self.location.href` and compiles its Wasm from bytes, both of which Workers forbid ([reproduction](https://github.com/lnorton89/metaplate/tree/main/examples/hosted/cloudflare)). Public dynamic image routes are CPU- and memory-intensive. Bound copy length
and component complexity, use stable path params rather than arbitrary query
strings, set an explicit cache policy, and apply deployment-level concurrency
and timeout limits. Never pass a request-controlled remote image URL into a
Satori component: allowlist asset origins so server-side rendering cannot be
used to reach private or link-local services. `remoteImageLoader` from
`metaplate/assets` enforces such an allowlist (see
[Images and assets](rendering.md#images-and-assets)). To refuse URLs your pages
did not emit, sign them; see [Signed image routes](signed-routes.md).
